# app/openclaw — module map

Root rules live in the repo-root `CLAUDE.md` (hard rules, domain rules, working style). This file is the "where does X live" index.

## Pipeline (runs every tick — `pipeline.run_once`, order matters)

| Module | Owns |
|---|---|
| `pipeline.py` | Orchestration: match → extract invoice files → draft claims (≤4/batch) → reconcile sent requests → poll Petcover → Telegram notifies. Per-claim error isolation (`_TRANSIENT_MATCH_FLAGS`); one claim's failure never kills the tick. |
| `vet_detection.py` | NetBank CSV rows → is-this-a-vet (keywords first, LLM fallback, `non_vet_merchants` denylist) → `vet_claims` rows. |
| `invoice_matching.py` | Gmail search per claim (`_build_queries`: merchant narrow+wide, spouse fallback, `-from:me` + SENT-label guards), LLM invoice extraction (cached in `email_extractions`), vision-OCR fallback for image-only scans (ADR-0010, `vision_ocr_attempts` 3-cap), `_pick_invoice` gates (ceiling ADR-0007, date plausibility, `_already_claimed`, closest-amount ranking), split/merge proposals (one invoice paid over several charges), invoice-request drafting when nothing found. |
| `claim_forms.py` | Petcover PDF form filling, per-visit invoice page extraction (`find_invoice_segment` text path / vision `page` slice path), `ensure_invoice_file`, pet auto-assign from printed patient facts, Gmail draft creation (`process_claim` single / `process_claim_batch` ≤4 same-pet), condition/pet setters used by Telegram + dashboard. |
| `claim_status.py` | Petcover reply polling → append-only `claim_status_events` (ADR-0008), reference learning from acknowledgements, mark-sent, correlation (pet + submitted pool, NO date windows), settlement parsing (amounts live in the PDF attachment). |

| Module | Owns |

No other module imports a provider SDK — except `gemini.py`, which is the Gemini implementation behind it. `_FALLBACK_MODELS` walks four Groq models on daily-budget exhaustion (per-model TPD, ADR-0017); `_is_daily_budget_exhausted` vs `_is_rate_limited` is the split that decides switch-model vs back-off-and-retry. |

| `gmail_client.py` | OAuth, `full_message_text` (includes PDF text — settlement breakdowns need it), attachment iteration. Read + drafts only; `send()` is forbidden (hard rule). |
| `db.py` | Schema (`CREATE TABLE IF NOT EXISTS` — live schema CHANGES to existing tables need manual DDL against `app/data/openclaw.db`), connections. |
| `telegram_bot.py` | **Slated for deletion by `openclaw-gateway-core`** — the gateway owns transport and two pollers on one token is a `409 Conflict`, so the cutover is atomic. Until then it is live and unchanged. Bot commands/callbacks (auth = single username), notify send helpers (`send_message_sync`, `send_document_sync`, `send_photo_sync`), 👍 ack on every incoming user message, `_append_result` (edits text OR caption — PDF alerts have no text). `/history` (paged claim-card images) and `/actions` (summary card + one tap-to-resolve card per outstanding action, capped at `ACTION_CARD_CAP`). |

| `claim_card.py` | Pillow renderers for the Telegram cards: `render` (month-grouped claim history) and `render_actions_summary` (what's waiting on Justin, blocked items separated). Status labels/colours mirror `templates/index.html`'s `status_chip`. Fonts resolve DejaVu (Docker, installed by the Dockerfile) → Windows → `load_default`. |
| `main.py` + `templates/` | FastAPI dashboard: claims list, flags, CSV upload, condition entry. |
| `scheduler.py` | APScheduler wiring for ticks + Gmail ingest. **`max_instances` defaults to 1 and nothing here overrides it**, so APScheduler already refuses an overlapping run — a guarantee that is invisible until you move to a scheduler without it. |
| `internal_api.py` | The OpenClaw gateway's way in: `/internal/tick`, `/internal/ingest`, `/internal/nudge`, secret-guarded (blank secret **refuses**, never runs open) and loopback-allowlisted. Thin wrappers only — no claims logic. `run_exclusive` holds a per-job in-process lock rebuilding the overlap protection cron lacks; it is valid **only** while uvicorn runs one worker (see the `CMD` comment in `app/Dockerfile`). Mints a correlation id per event so a failure crossing gateway → app is traceable. |
| `gateway_client.py` | The `LoggedBot` of the gateway era: the ONE seam for outbound messages once the gateway owns the bot token. Every send records to `telegram_messages`, so anything shelling out to the CLI directly sends a message that never lands in the log — `test_nothing_outside_gateway_client_shells_out_to_the_gateway` fails if a module imports `subprocess` or reads `config.OPENCLAW_CLI`. All CLI argv construction lives in one `_argv` function because the flag names are unverified until the gateway spikes run. |
| `mcp_server.py` | The claims surface for the gateway's agent, JSON-RPC over `POST /mcp`, same shared secret as `/internal`. **Reads plus proposals** as of ADR-0027 — a `propose_*` tool writes a `pending_proposals` row and sends a Confirm card, and nothing here can reach `proposals.commit` (asserted, not conventional). Twelve tools enumerated in `TOOLS` — no dynamic registration, because the inventory is the `gmail-isolation-boundary` enforcement surface *and* a per-turn token cost (every schema ships on every turn; measured 1,172 chars, ~4.9k-token turns against Groq's 12k TPM). Implementations are reused from `agent._build_impls`, selected **by name from `TOOLS`**, so the `propose_*` functions in the same dict are unreachable. Hand-rolled rather than the `mcp` SDK: that pulls starlette 1.3.1 against this app's `fastapi<0.42` pin. Validated with the gateway's own `mcp probe`. Tools appear to the agent as `claims__<name>`, which is what `tools.allow` must match. |
| `commands.py` | The app's command surface with **no transport in it**: the pure `handle_*` functions (moved out of `telegram_bot`, which aliases them so both paths call the identical function), the card builders, and `dispatch(name, args, username)` — what `/internal/command/<name>` calls when the plugin forwards a tap. Cards are built once here in the **gateway's** button shape (`{"label", "command"}`); `telegram_bot._action_keyboard` renders that as `cmd:<command>` callbacks rather than being a second builder. `/mark <id>` reserves two words, `sent` and `reviewed` — a condition genuinely called either cannot be set by button. ADR-0027. |
| `notify.py` | The ONE outbound seam, and the switch between transports. `send_text` / `send_card` / `send_document` route to `gateway_client` or to `telegram_bot`'s `*_sync` senders by `config.TELEGRAM_UPDATER_ENABLED` (default on = the app polls, which is pre-cutover). Callers hand it the **gateway** button shape and the PTB path converts, deliberately: the gateway's shape is the one with hard constraints (58 UTF-8 bytes, registered verbs only), so they are exercised on every send from today rather than first thing on cutover day. Every failure logs at ERROR and returns False — an unattended tick must not die on a lost notification, and must never look like it sent one. |
| `pending_flows.py` | Flows that own Justin's **next typed message**: entering a condition free-hand, and walking a multi-item invoice a line at a time. `claim_text(chat_id, text)` is THE decision — `None` means the agent gets the message, anything else means a flow consumed it — and both the PTB handler and the gateway's `before_dispatch` hook call it, so the transports cannot disagree about whether the agent sees a typed condition. Durable (`pending_flows` table) because after the cutover the tap, the claim check and the reply are three separate requests; two module dicts could not span that, and a restart in between would hand `condition_text` to a model. Task 0.10: the hook is reached via `api.registerHook("before_dispatch", …)`, which runs *after* command routing, so a slash command still works mid-flow. |
| `proposals.py` | The ONE commit path for a proposed mutation, and the durable record of one (`pending_proposals`). `record()` is what a `propose_*` tool reaches; `commit()` is reachable only from a confirm tap and is the only code that writes. The action switch (`execute`) moved here verbatim from `telegram_bot._execute_action`, which now delegates — that module dies at the cutover and its behaviour must not go with it. Durable because the proposal and the tap are now separate requests in separate runtimes; `confirmed_at` makes a tap single-use, since Telegram redelivers and a double mark-sent is a second Petcover submission. ADR-0027 (supersedes 0025's gate *location*: the MCP surface cannot gate its own commit, because the gateway's MCP client declares no `elicitation` capability). |
| `media_outbox.py` | The ONE path between the two containers. Cards are Pillow bytes; the gateway CLI wants a path, and refuses any path outside its own fixed media roots. So: one shared volume, `/data/outbox` here and `<stateDir>/media` there, and `publish()` returns the **gateway's** path so a caller cannot hand over one that will be refused. Write-then-rename (a truncated PNG sends "successfully" and arrives corrupt); random names, not claim ids; swept on publish. Never widen this to `app/data`, and never set the gateway's `media.localRoots` to `"any"` — that one word disables the whole control. |
| `../gateway-plugin/` | Not Python — the plugin that registers the app's slash commands **inside** the gateway, so `command` buttons have something to invoke. Forwards to `/internal`, holds no claims logic, claims Telegram's per-chat command menu, and reports at boot what `registerCommand` accepted. Four things bite: `definePluginEntry` is mandatory (a plain export loads and never runs); `register()` must be synchronous (its return value is discarded, so an `async` one loses every registration); the SDK import must be the absolute container path, not the documented bare specifier; and a manifest + `package.json` with `"openclaw": {"extensions": […]}` are both required. **`registerCommand` does not report a collision** — the gateway logs it asynchronously ~1s later, so the boot report proves the plugin *ran*, never that it *owns* the names. `scripts/gateway_preflight.py` reads the log for that. |
| `config.py` | All env; `.env` loaded from cwd. Container paths are `/data/...` (compose binds host `app/data`). The **gateway's** secrets live in the repo-root `.env`, not this one — compose interpolation cannot read `app/.env`, and pointing the gateway at it would hand it the Gmail credential. See `.env.example`. |
| `agent.py` | Telegram free-chat agent (LLM tool-calling; reads are direct, mutations are *proposals* confirmed by a tap). `system_prompt()` injects the real pet list **and today's date** — the model invented pet names when left to guess, and guessed at "July 2025" with no date to anchor on. It cannot browse or search mail, but it has **three named sweeps** that do touch Gmail: `reconcile_sent_invoice_requests`, `rematch_claims`, `poll_petcover_now`. They act directly (not proposals) because the tick already makes those exact calls unattended, and they're safe under ADR-0014 replay only because each is idempotent — ADR-0016. No code/spec/doc access: claim-level "why" is `claim_detail`, anything about the implementation it must decline. |
| `netbank_csv.py` | CSV upload parsing/dedupe into `bank_transactions`. |
| `tasks.py` / `reminders.py` / `gmail_ingest.py` | Assistant side (email → tasks/reminders), independent of claims. |
| `db_backup.py` | Drive backup of the SQLite DB. |
| `../gateway-workspace/*.md` | Not code — the agent's workspace files (`AGENTS`, `IDENTITY`, `USER`, `SOUL`, `TOOLS`, `HEARTBEAT`), shipped into the gateway at deploy and injected into **every** agent turn. Authored here rather than interviewed for, and versioned with the app, so a behaviour change is a reviewable diff. Two consequences: they are a per-turn token line item (6,508 chars — the stock templates were 14,341), and **nothing enforceable belongs in them**. The no-send rule, the required-field rule and the proposal gate are code; the stock prompt was observed claiming it had checked mail it had no credential for. ADR-0024/0023. |

## Gotchas that repeat

- Every notify message must carry the claim `#id` — Justin acts by id (`/mark`, `/pet`); regression test enforces it. This applies to the chat agent too: it used to be told the opposite ("never internal ids") and produced answers he couldn't act on.
- `notify_claim_states` is a **change-feed**, not a state list — it dedupes on `(telegram_notified_status, telegram_notified_flag)`, so a claim that stays outstanding is announced once and never again. `claim_status.pending_actions()` + the daily `pipeline.nudge_stale_actions` job are the state-based counterpart.
- `pending_actions()` is one entry per **claim** except for `SUBMISSION_LEVEL_ACTIONS` (currently `mark_sent` alone), which fold to one entry per submission carrying `claim_ids` + `group_id` + `members`. One Gmail draft is one email, so N cards asked for N-1 taps too many and taps 2..N hit an already-sent claim. The collapsed entry keeps `claim_id` = lowest member so `sent:{id}` tokens and `mark_sent` are untouched. Group id is `claim_status.submission_group_id` → `S6+7`, derived not stored (a column would need manual live DDL).
- `draft_id` is overloaded (claim drafts AND invoice-request drafts), so `invoice_request_sent_at IS NULL AND draft_id IS NOT NULL` matches almost every claim. Use `flag = 'invoice_request_drafted'` to find awaiting-invoice-request claims.
- Telegram messages with a PDF are documents: edit the **caption**, not text (`_append_result`).
- `message_log.mark_processed` refuses rows that already carry an `error`. PTB runs its error handler *inside* `process_update`, so a failed update otherwise reaches `mark_processed` looking successful and gets silently dropped from the replay queue.
- Outbound logging lives in `LoggedBot`, so anything that constructs a plain `telegram.Bot` bypasses the message log. The three `*_sync` senders use `LoggedBot` for exactly this reason.
- ERROR means *Justin must act*. Transient network failures are WARNING (`pipeline._is_transient`) — a Gmail `IncompleteRead` used to log a full traceback and read like a crisis.
- The updater task is fire-and-forget: nothing awaits it, so its death is silent. `polling_alive()` + `pipeline._watchdog_telegram_polling` (SIGTERM, compose restarts) is the safety net.
- Never replay a provider's whole assistant message back into `chat()`'s tool loop — `_assistant_turn` whitelists role/content/tool_calls. `model_dump()` echoed gpt-oss-120b's `reasoning` field and every following request 400'd (`reasoning is not supported with this model`). Whitelist, not a `reasoning` blacklist: the next output-only field would repeat it.
- Chat replies are sent with **no `parse_mode`**, so markdown arrives literally. The fallback models answer with pipe tables unless the prompt forbids it (`test_prompt_forbids_markdown_for_a_plain_text_channel`).
- Rate limits are two different failures: per-MINUTE tokens → back off, retry same model; per-DAY tokens → switch model, one attempt each (retrying can't free a daily cap). Only the 429 *body* names which — the headers never mention TPD.
- One charge can pay TWO invoices (one per pet). `_complement_for` finds the second and `_apply_match` creates a sibling claim on the same `transaction_id` with its OWN `matched_email_id`/invoice/pet; `invoice_data.charge_note` records the pairing. It refuses when two candidates could both close the charge — ambiguity is not resolved. Before this, the remainder just became `possible additional invoice — unexplained $X` and the second pet was never claimed (ADR-0019).
- A receipt's SERVICE date is not its payment date: The Shire Vet's 19 Jun and 30 Jun visits were both charged 6 Jul, and `INVOICE_MATCH_WINDOW_DAYS` is 3, so both real invoices were rejected. `_paid_on_charge_date` accepts an invoice when one line of its own text carries both the charge's date and that invoice's amount. Don't "fix" this by widening the window — the window is what stops one visit's invoice being taken for another's.
- `invoice_data.claimable_amount` is **per claim**, not per invoice: a per-pet split (ADR-0019) gives each sibling claim its own share there, which is exactly what `_charge` puts on the form. `invoice_data.split_note` is the human-readable record of that split (subtotal + every sibling id/pet/share) — don't read a reduced claimable as a mis-extraction. `check_split` holds every guard with no writes (the agent's pre-tap validation); `split_between_pets` writes.
- Two different things are called a split. `split_proposals` / `split:` callbacks = several bank CHARGES for one invoice (merge) and per-item CONDITION splits. The per-PET split is `claim_forms.split_between_pets` and the `split_pets` proposal action. Same word, three axes.
- An edit arrives as an `edited_message` update where `update.message` is **None** — always `update.effective_message`. `filters.TEXT` matches edits, so `.message.text` crashed the text handler and the log wrote a kind-`other` row with an empty summary (2026-07-27).
- A reply to a card gives you the target for free: `telegram_bot._replied_to_claim_id` reads `Claim #N` from the parent's text/caption or its callback data, and returns None unless exactly one claim is named. Every `propose_*` tool takes `claim_id` — without one the model fabricated arguments out of the tool schema's own description strings.
- Status words live in ONE map: `status_labels.py` (`LABELS` + `label()` for chips, `needs()` for `/basic`'s what's-needed line). They used to be three hand-synced copies plus pipeline's notify strings, linked only by a "mirrors index.html" comment. Don't add a fourth — `test_one_status_vocabulary_no_second_map` fails if you do. `claim_card._STATUS_COLOURS` is keyed by **status**, not by wording, for the same reason (ADR-0021).
- A `matched` claim's LABEL is derived, not stored, so the dashboard word and `vet_claims.status` legitimately differ: `blocked_insurer` → "Blocked: no claim process", `set_condition` → "Needs condition", `assign_pet` → "Needs pet". It reuses `claim_status._action_kind_from_row` (the row-only half of `_action_kind`) so a label can't disagree with the action list. Seven live claims read "Matched" for weeks while being permanently blocked on Bow Wow's undefined process.
- Petcover's letter names the document it wants, and `requested_document` / `requested_document_date` on the event carry it (`claim_status.extract_requested_document`, regex only). The ask's own filler MUST be consumed or it becomes the "document" — a refactor dropped that and produced `information in order for us to review the` as the thing to chase, caught by a dry run against real mail while the unit tests passed. A capture under 4 chars is rejected because one letter's body ends mid-sentence at "for us to review the".
- The requested DATE resolves to a visit, usually on a **different claim** than the letter is about: `invoice_matching.find_visit_by_date` (claims first, extraction cache second, every match returned, never a nearest-date guess). Live: the request is on claim #8, the date is claim #6's invoice 1000229. The resolved invoice identifies the visit and is NOT the document — consult notes are clinical records only the vet holds, so nothing is attached in their place.
- Two nudge jobs exist with different cadences and scopes — don't merge them. `nudge_stale_actions` is daily, keyed on charge age, and reports only the oldest. `nudge_unanswered_vet_requests` is **weekly** (`VET_NUDGE_DAY`, default `mon`) and lists every unresolved vet-owed request with clinic, document, resolved visit, and days to the **treatment-anchored** deadline (`INFO_REQUEST_DEADLINE_DAYS`), because that is the clock that kills a claim. Silent when nothing is outstanding.
- A treatment date is **not** a charge date, and the deadline hangs off the treatment (Petcover: "within one year of your pet receiving treatment"). `claim_status.treatment_date()` takes the EARLIEST date the invoice states — its own or any line item's — since an invoice billing several visits expires on its oldest; with no invoice it falls back to the charge date and the message says `assumed = charge date`. Live proof of the gap: The Shire Vet treated Aari 19 Jun and Echo 30 Jun 2026, both charged 06/07/2026 — anchoring on the charge over-granted 17d and 6d. Nothing bounds that gap. **`_policy_year_key` still uses the charge date for excess/cap** — same question, different money, deliberately not aligned (BACKLOG).
- An `info_requested` label depends on `owed_by` from the event detail: vet → "More vet info required", Justin → "Petcover needs info from you", unrecorded → neutral "Info requested". Never default it — Petcover asks the vet as often as Justin and he's only Cc'd, so naming the wrong party is how the chase never happens.
- `email_extractions` caches successful extraction FOREVER; invalidate the row if you change what extraction must return.
- Vision attempts are refunded on `LLMUnavailableError` (provider outage ≠ unreadable scan).
- Invoice identity across claims: `invoice_number` first, else amount+date (`_already_claimed`).
- **`claim_status.apply_event` is the ONLY writer of `vet_claims.status`.** It appends the event, then applies the state if `TRANSITIONS` declares the move; an undeclared move leaves the state alone and flags the claim naming both states and the event id. Callers keep their own field writes (`invoice_data`, `draft_id`, `claim_file_path`) and hand over the state — always *after* their own `flag = ?` write, or that write wipes the refusal it caused. `test_no_module_outside_claim_status_writes_the_status_column` fails if a module writes the column directly. Nine statements across three modules used to; six of them appended nothing, which is how the 2026-07-27 re-read moved four claims backwards and the 2026-07-28 repair had to infer a claim's prior state from an absence.
- Event types split three ways, and the split is data rather than an `if`. `STATE_EVENTS` maps type → a fixed target state. `STATELESS_EVENTS` are recorded and move nothing (`unclassified` is here — it is a review-queue entry, and writing it to status would regress an acknowledged claim). `BACKFILL_EVENT` (`state_backfilled`) is the third and the only exemption in the machine: state-bearing, target read per-claim from `detail["status"]`, and not subject to `TRANSITIONS` because it *asserts* a state the log has no path to. Don't move it into `STATELESS_EVENTS` — `design.md` originally had it there, which would have made the backfill a no-op and then let Phase 2 reset all 19 backfilled claims to `pending_match`.
- The fold seeds at `CREATED_STATE = "pending_match"`, not at `None`. No creation event exists to consume `None`→`pending_match`, so seeding at `None` refuses every claim's first event. `TRANSITIONS[None]` stays as the notional creation step; nothing folds through it.
- `/health`'s `state_projection_disagreements` is Phase 1's whole point: claims whose stored status differs from what their own events project. **Non-zero means a claim moved without an event** — a writer bypassing `apply_event`. It does **not** detect a wrong transition table: a refused move leaves the column alone *and* `_fold` skips the same event, so detector and enforcer share `TRANSITIONS` and agree by construction. A table defect surfaces as a claim flag, not as a count. Nor does zero mean much on a backfilled claim, whose seed carries the very column being compared — 19 of the 22 live claims are in that position. Judge the shadow period on claims that **actually transition** during it; a quiet week proves nothing. It is logged at WARNING, never ERROR (ADR-0015 reserves ERROR for "Justin must act", and he cannot fix a projection bug), and `pipeline.compare_state_projection` runs *before* the Gmail-auth check so an auth outage can't skip the report. The comparison deliberately writes nothing: a check that repairs what it measures has measured nothing. Read 19 before the 2026-07-30 backfill, 0 since.
- Not built yet (Phase 2): `revert_state`, the claim timeline, and the projection being authoritative. Until then the column is what everything reads, and the projection only watches. There is **no reversion handling at all** — `_reverted_event_ids` and the `state_reverted` event type were removed 2026-07-31 after the retro found the skip had never fired (zero live rows, and `apply_event` could not write one because the type was stateless). Consequence to rely on: appending a reversion today hits the unknown-event-type refusal and flags the claim, rather than being recorded and ignored. Phase 2 rebuilds both, and must handle reverting a reversion — the deleted version never did. ADR-0022's amendment.

## The move this codebase keeps making: one writer, one declared table, one mechanical guard

Five times now, the same shape has fixed the same class of bug: **a rule enforced by
convention across N callers gets collapsed into a single writer that owns a declared
table, plus a test that fails if a caller bypasses it.** Reach for this when you find
yourself writing "remember to also update X" — that sentence is the smell.

Not a pattern catalogue. These five are the instances; the guard column is the honest
state of each, because a convention with no check is what every one of these incidents
was before it became an incident.

| Rule | Was | Collapsed to | Mechanical guard | What it cost first |
|---|---|---|---|---|
| Claim status writes | 9 statements, 4 modules, 6 appending nothing | `claim_status.apply_event` + `TRANSITIONS` | **yes** — `test_no_module_outside_claim_status_writes_the_status_column` (self-checked: asserts its own regex fires on a violation) | 2026-07-27 re-read moved 4 claims backwards, restored from backup; 2026-07-28 repair had to infer a prior state from an absence |
| Status wording | 3 hand-synced maps + notify strings | `status_labels.py` | **yes** — `test_one_status_vocabulary_no_second_map` scans every `templates/*.html` for every `LABELS` value, and checks the `status_words` global is registered (Jinja renders a missing global as empty string, so a broken lookup would blank the chip silently). Corrected 2026-07-31: this row read "partial", citing an `index.html:235` hardcode that no longer exists — the line renders `status_words['pending_match']`. The doc was stale, not the code | 7 claims read "Matched" for weeks while permanently blocked (ADR-0021) |
| Telegram sends | plain `telegram.Bot` per caller | `LoggedBot` | **partial** — `test_core.py:776` asserts the app's bot IS a `LoggedBot`; nothing stops a second construction | a failed update reached `mark_processed` looking successful and left the replay queue (ADR-0014) |
| LLM provider access | per-caller SDK calls | `llm.py` seam (`chat`/`extract`/`extract_vision`) | **none** — convention only | ADR-0009; a 403 took extraction and chat down together because all four fallback models are one provider |
| Host access to the live DB | 4 plain `sqlite3.connect` sites | *not collapsed* | **none** — `docs/failure-modes.md` standing gap #1 | 51-minute total outage 2026-07-25; the rule was then broken 4 more times in one session by people who had just read it |

Two related moves with 3+ instances each, both forced by this repo's constraints
rather than chosen:

- **Shadow-compare before authority.** Never let a new derivation write until it has
  agreed with the old one for a while: the state machine's Phase 1 (`pipeline.compare_state_projection`,
  count on `/health`), the 2026-07-28 repair's dry-run diff, `check_split` (all guards,
  no writes) vs `split_between_pets` (writes). The reason is on record — the last
  state-writing change that skipped the comparison regressed four claims.
- **Derive, don't store.** `submission_group_id` -> `S6+7`, a `matched` claim's label via
  `_action_kind_from_row`, `status` as a projection of its event log. Partly because a
  new column needs hand-run `ALTER TABLE` on the live DB, partly because a second
  answer to the same question eventually disagrees with the first.

When you reach for the collapse, it needs all four parts or it decays back: the
declared table, the single writer, the guard test **named**, and a shadow-compare phase
if the thing being collapsed *writes* rather than renders. Wording needed no shadow
phase; the status machine did.

**One instance is not a pattern.** Append-only-log-plus-projection (`claim_status_events`),
provider-fallback-with-budgets (`llm._FALLBACK_MODELS`), durable-log-with-replay
